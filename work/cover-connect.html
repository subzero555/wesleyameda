Cover Connect

One verified profile a person can show to several insurers, instead of filling the same forms four times.

Role
Development. Concept by April Odhiambo
Platform
Mobile web and Android
Year
2026
Status
Working prototype, no backend yet

A note on what this is

This is a prototype and the page says so before it says anything else. Every screen works, the flows are complete end to end, and behind them sits a mock that stores data in the browser and returns it after a made up delay. The verification codes are fixed, the tokens are strings that mean nothing, and no insurer receives anything.

That is worth stating clearly rather than burying, because a demo that behaves exactly like a real product is the easiest thing in software to misrepresent. What it proves is the interaction design and the data model. What it does not prove is anything about underwriting, compliance or security, and those are most of the work still to come.

The prototype exists to find out whether the idea is worth the backend, not to stand in for one.

The problem

Applying for cover in Kenya means assembling the same documents repeatedly. Identity card, tax number, driving licence, beneficiaries, medical history, typed again into each insurer's form, each with its own idea of what a date looks like. Comparing two offers means doing the whole thing twice, so most people do not compare, they take the first quote that arrives and hope.

The information does not change between applications. Only the recipient does. That is a strong hint that the profile should be the durable object and the application should be a thing you point it at.

What it does

You build one profile, once, and it fills in as you go rather than demanding everything at the start. When you apply to an insurer you choose which parts of it they receive, and consent is a record you can look at later rather than a checkbox you passed through. Applications and issued policies then live in the same place, so cover is something you can see rather than a document you have lost.

  • A single profile covering identity, tax number, licence, beneficiaries and medical details
  • Selective sharing per insurer, with consent recorded as its own object
  • Browse and compare cover across several partner insurers
  • Application tracking from submission through to a decision
  • A wallet of issued policies
  • Guest mode, so the app is explorable before an account exists
  • Profile completeness scoring, which is the nudge that gets a form finished

Designing against a contract

The mock is written as a single module that every screen calls, and its method signatures are deliberately the specification the eventual server has to satisfy one for one. Authentication, profile, document upload, applications, consents, policies and notifications are all defined there with fixed shapes, and the shared type definitions are the source of truth that a real backend would import rather than reinvent.

This is the difference between a prototype that helps and one that has to be thrown away. The screens are not wired to a pretend server that happens to work. They are wired to an interface, and swapping the implementation underneath is the actual remaining task rather than a rewrite. It also means the seams are visible now, which is when it is cheap to notice that completeness scoring has no business being calculated on the client.

A simulator for the other side

On a wide screen the app renders inside a phone frame next to a panel that does not ship to users. It can toggle network conditions and fire the actions an underwriter would take, approving an application, requesting a document, issuing a policy, so the states that are normally impossible to reach without a working insurer can be walked through in seconds.

Building that harness early paid for itself immediately. Most of the interesting screens in an insurance application are the ones that depend on somebody else acting, and without a way to trigger those you end up designing the happy path in detail and the rest from imagination.

Cover Connect running as an Android build

How it was built

A React single page application in TypeScript, built with Vite and styled with Tailwind, with the theme defined once as tokens rather than scattered through components. The root of the app is a small state machine moving between onboarding, authentication and the tabbed application, which keeps navigation legible in one file instead of spread across a router.

Capacitor wraps the same web build into a native Android package, so there is one codebase and one set of screens rather than a web version and an app version drifting apart. The layout switches on whether it is running natively or under a narrow viewport, which is what allows the desktop simulator to exist without leaking into what a user on a phone sees.

Where it goes

A real server implementing the interface the mock already describes, and that is where the difficult part starts rather than ends. Documents of this kind are regulated, consent has to be provable after the fact rather than merely recorded, and a partnership with any insurer is a commercial conversation rather than an integration ticket.

The idea is April Odhiambo's, a student and innovator at the Siaya Community Digital Hub. I built it. That division is worth stating plainly, because the hard part of this one was never the React: it was noticing that the profile is the durable object and the application is a thing you point it at, and that insight arrived with the brief rather than during the build.
